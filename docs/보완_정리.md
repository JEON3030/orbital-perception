# 보완 정리 — 정확도/의미 인식 흡수 + 양쪽 구동 + 통합지표

**2026-07-31.** 이 문서는 orbital-perception 프로젝트가 "전력 우선(energy-first)"에서
"정확한 장면 의미 인식 + 저전력 온보드 실증"으로 확장된 과정을 한곳에 정리한다.
계기는 같은 캡스톤의 다른 구현([`park-hyun-su/syntax_inference`](https://github.com/park-hyun-su/syntax_inference))과의
비교였고, 거기서 드러난 우리 쪽 공백을 메우는 방향으로 진행했다.

---

## 1. 두 프로젝트 비교 — 강점이 정확히 반대

| 항목 | **orbital-perception (이 저장소)** | park-hyun-su/syntax_inference |
|---|---|---|
| 핵심 관점 | **전력/에너지 (mJ/frame, frames/J)** | 정확도/시각화 (mIoU, 얇은 클래스) |
| 인식 종류 | YOLO11 탐지 + 인스턴스세그 (COCO) | 시맨틱세그(SegFormer B0~B5) + 탐지 |
| 실측 하드웨어 | ✅ **젯슨 실기 7W 실측** | ⚠️ i5 노트북 CPU (젯슨 미실행) |
| TensorRT | ✅ **FP16 완료** | ❌ 미룸 |
| 전력 계측 | ✅ tegrastats 내장 | ❌ 없음 |
| 시맨틱 세그 | ❌ (보완 전) | ✅ 도로/항공, LVM 백본 곡선 |
| 정확도(mIoU) | ❌ (보완 전) | ✅ mIoU 0.650 (CamVid) |

**결론:** 두 프로젝트는 같은 요구(위성 온보드 AI, 테슬라식 인식 시각화)의 서로 다른
반쪽이었다. 이 저장소는 "온보드에서 얼마나 적은 전력으로 실제로 도는가"에, 상대는
"무엇을 얼마나 정확히 보는가"에 깊었다. → **상대의 강점을 이 저장소의 에너지 프레임으로
흡수**하기로 했다.

## 2. 보완한 것 (4가지)와 장점

### 2.1 시맨틱 세그멘테이션 — `semantic.py` / `semantic.sh`
- **무엇:** SegFormer-B0 시맨틱 세그. `road`(Cityscapes 19클래스), `aerial`(ADE20K 150클래스).
  픽셀 전체를 도로·건물·식생·하늘·수면 등 **장면 클래스**로 분류.
- **왜:** YOLO COCO에는 건물·도로·식생·하늘 클래스가 없다. 위성/항공 관점의 토지피복·
  지형 인식은 시맨틱 세그가 있어야 가능하다. 우리 쪽 최대 공백이었다.

### 2.2 장치 추상화 — `device.py`
- **무엇:** `--device auto|cpu|cuda` 한 곳에서 결정. fp16, **CUDA 비동기 sync 시간보정**,
  젯슨 감지, OOM 판정.
- **왜:** 젯슨(온보드 GPU)과 노트북(시연 CPU)을 **같은 코드**로. CUDA는 비동기라 sync 없이
  시간을 재면 mJ/frame이 실제의 1/100로 찍혀 거짓이 된다 — 이를 막아 실측 신뢰성 유지.
  "GPU인 줄 알았는데 CPU로 돌던" 실수를 리포트에 장치를 찍어 잡는다.

### 2.3 통합 지표 mIoU-per-Joule — `metrics.py`
- **무엇:** 혼동행렬 기반 mIoU + **mIoU-per-Joule = mIoU ÷ (프레임당 에너지[J])**.
  라벨 폴더 평가(`eval_folder`)와 지표 자체검증(`--selftest`) 포함.
- **왜:** 정확도(상대의 축)와 전력(우리 축)을 **한 숫자**로 비교. 위성 온보드의 진짜 질문
  "전력 예산 안에서 정확도를 얼마나 사는가"에 직접 답한다. TensorRT·해상도·백본 선택이
  이 한 값으로 우열이 갈린다.

### 2.4 웹앱 통합 — `webviz.py`
- **무엇:** 라이브 추론 탭에 `시맨틱세그` 작업 + 도메인(도로/항공) + 장치(GPU/CPU) 선택기.
  대시보드에 보완 성과 반영.
- **왜:** 코드 없이 브라우저에서 새 기능을 시연·비교.

## 3. 실측 결과 (전부 이 젯슨 Orin Nano에서, 추정치 없음)

### 3.1 시맨틱 세그 — 장치 대조 (SegFormer-B0, sample.jpg)
| | 젯슨 GPU (fp16, 온보드) | 노트북 CPU (시연) |
|---|---|---|
| 속도 | **7.4 FPS** | 0.38 FPS |
| 총 에너지 | **776~927 mJ/frame** | 16,110 mJ/frame |
| 순수추론 에너지 | 163~222 mJ/frame | — |
| 효율 | ~1.08 frames/J | 0.06 frames/J |

→ **온보드 GPU가 노트북 CPU보다 약 17배 에너지 효율.** 이 수치 자체가 "왜 온보드
저전력 하드웨어가 필요한가"의 증거다.

### 3.2 통합 지표 예시
mIoU 0.650(park-hyun-su B0 기준선) 가정 시:
- 순수추론 에너지(222 mJ) 기준 → **약 3.98 mIoU·J⁻¹**
- 실제 mIoU는 `python metrics.py --images <img> --labels <label> --domain road`로 산출.

### 3.3 (기존) YOLO TensorRT FP16 vs PyTorch, 7W
| task | PT mJ/frame | Engine mJ/frame | 개선 |
|---|---|---|---|
| detect | 429.9 | 283.1 | −34% (순수 −51%) |
| segment | 619.0 | 436.5 | −29% (순수 −45%) |

## 4. 실행법

```bash
# 시맨틱 세그 (젯슨 GPU / 노트북 CPU)
./semantic.sh input/sample.jpg                 # road
./semantic.sh input/x.png --domain aerial      # aerial
./semantic.sh input/x.jpg --device cpu         # 노트북 CPU 시연

# 통합 지표
python metrics.py --selftest                                       # 수식 검증
python metrics.py --images <img폴더> --labels <라벨PNG폴더> --domain road

# 시각화 웹앱 (대시보드 + 라이브: YOLO+시맨틱, GPU/CPU)
./webviz.sh          # http://<보드IP>:7860
```

## 5. 구현 함정과 해결 (재현·유지보수용)

1. **transformers ↔ torch 2.5 / hf-hub 1.x 충돌.** 공유 venv의 huggingface-hub(1.x)와
   JetPack torch(2.5) 사이에 맞는 transformers가 없었다(신버전은 DTensor 요구, 구버전은
   hf-hub<1.0 요구). → orbital-perception 전용 `_deps/`(transformers 4.46 + hf-hub 0.26 +
   tokenizers 0.20)를 sys.path 앞에 격리 설치. torch/GPU는 venv 것 사용 → **다른 프로젝트를
   안 건드림.** `_deps/`는 .gitignore(재설치 명령은 .gitignore에 주석).
2. **torchvision 스텁 ↔ transformers 공존.** 이 젯슨엔 torchvision 메타데이터만 남고
   바이너리가 없어 `perception.py`가 NMS만 스텁 주입한다. transformers가 이를 오판해
   `torchvision.transforms`를 import하려다 죽었다. → 스텁에 `__spec__` 부여(find_spec
   크래시 방지) + `semantic.py`에서 `import_utils._torchvision_available=False`로 못박음.
   SegFormer는 torchvision이 필요 없다.
